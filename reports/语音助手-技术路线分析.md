# MY PLAN 语音助手 — 技术路线全面分析

**日期**：2026-07-15 | **目标**：实现完整的语音对话式计划创建闭环

---

## 一、核心闭环定义

```
用户说话 → STT识别 → NLU填槽 → 状态机决策 → TTS合成 → 播放语音 → 继续聆听
    ↑                                                                      ↓
    └──────────────────────── 循环直到槽位填满 ─────────────────────────────┘
```

## 二、各环节技术分析

### 环节 1：音频采集

| 项目 | 方案 |
|------|------|
| 当前实现 | `AudioRecorder.kt` — `AudioRecord` 16kHz mono PCM 16-bit |
| 触发方式 | App 启动后自动开始录音 |
| 静音检测 | RMS（均方根）阈值 500，连续 25 帧静音判停 |
| 回声处理 | TTS 播放时 `stopListening()`，播完 +300ms 缓冲后重启 |
| 状态 | ✅ **已跑通** — 录音+静音检测正常工作 |
| 风险 | 无 |

### 环节 2：语音转文字（STT）

| 项目 | 方案 |
|------|------|
| 当前实现 | `CloudSttService.kt` — OkHttp WebSocket |
| API | `wss://openspeech.bytedance.com/api/v3/sauc/bigmodel_nostream` |
| 鉴权 | `X-Api-Key` header |
| 协议 | WebSocket 二进制协议（4 字节 header + payload_size + payload） |
| 流程 | ① WebSocket 握手 ② 发送 Full Client Request（JSON 配置）③ 发送 PCM 音频包 ④ 发送最后一包（标记 isLast）⑤ 接收 JSON 响应 → 提取 `result.text` |
| 状态 | ✅ **已跑通** — 中文识别准确，延迟 < 1.5s |
| 费用 | 火山引擎计费（小时版 volc.seedasr.sauc.duration） |
| 风险 | 无 |

**踩过的坑：**
- Android SpeechRecognizer → OPPO 国行无 Google 语音引擎 → ERROR_CLIENT
- Intent 拉起系统语音输入 → OPPO 无处理 APP → ActivityNotFoundException
- REST HTTP 调用大模型接口 → 返回空 JSON（需要 WebSocket）
- WebSocket 二进制协议最后一包标志 0x23（需 4 字节负数序号）→ 0x22（无需序号）
- 响应解析未跳过 4 字节 Sequence 字段 → 读错位

### 环节 3：自然语言理解（NLU）

| 项目 | 方案 |
|------|------|
| 当前实现 | `SlotFiller.kt` — 纯规则引擎（正则+关键词） |
| 槽位 | `plan_name`（必填）、`reminder_times`（必填）、`repeat_mode`（必填，默认"每天"）、`category`（选填，默认"日常"） |
| 解析顺序 | ① 取消词检测 → ② 确认词检测 → ③ 时间提取（正则可识别"早上8点""晚上8点""早上8点和晚上8点"等多时段格式）→ ④ 重复模式提取（每天/工作日/自定义星期）→ ⑤ 分类提取 → ⑥ 剩余文本清洗为计划名称 |
| 状态 | ✅ **已跑通** — 规则覆盖 80% 常见表达 |
| 增强方案 | V1.5 DeepSeek Function Calling（`VoiceApiService.kt` 已写，未接入） |
| 风险 | 复杂表达需要 DeepSeek 增强 |

### 环节 4：对话状态机

| 项目 | 方案 |
|------|------|
| 当前实现 | `VoiceConversationManager.kt` — Kotlin `sealed class ConversationState` |
| 状态 | `Dormant` → `Listening` → `Processing` → `Asking(missingSlot)` → `Confirming(planData)` → `Success(planName)` |
| 追问逻辑 | 按优先级追问：① plan_name → ② reminder_times → ③ repeat_mode |
| 确认逻辑 | 用户说"确认/好的/行/可以" → 创建计划；说"不对/改" → 重新来 |
| 取消逻辑 | 用户说"取消/算了/不用了" → 退出对话 |
| 状态 | ✅ **已跑通** — 状态流转正确 |
| 风险 | 无 |

### 环节 6：文字转语音（TTS）⚠️ 当前阻塞点

| 项目 | 方案 |
|------|------|
| 当前实现 | `CloudTtsService.kt` — HTTP POST → 解码 base64 → MediaPlayer 播放 |
| API | `https://openspeech.bytedance.com/api/v3/tts/unidirectional` |
| 鉴权 | `X-Api-Key` + `X-Api-Resource-Id: seed-tts-1.0` |
| 音色 | `zh_female_shuangkuaisisi_moon_bigtts`（豆包 1.0 模型） |
| 响应格式 | JSON `{ "code": 0, "data": "<base64 MP3>" }` |
| 当前问题 | **MP3 只拿到第一个分片（~1200 字节），不是完整音频。V3 SSE 流式返回多块 JSON，每块一个 `data` 片段，需要拼接所有片段再解码** |
| 根因 | `readBytes()` 可能因 SSE 格式提前返回，或 MediaPlayer 准备失败（Prepare failed: status=0x1） |
| 状态 | ❌ **阻塞中** — API 已连通，数据已返回，但分片拼接未实现 |

**踩过的坑：**
- Android TextToSpeech API → OPPO 无中文 TTS 引擎 → status=-1
- V1 端点 + V3 格式 → unmarshal 错误
- V3 端点 + V3 格式 → 返回单分片（1197 bytes，0.05 秒）
- V1 端点 + V1 格式 → 返回 96 bytes 错误信息
- V3 端点 + V1.0 Resource ID → 数据到达但分片不完整

**待修复方案：** 累积读取所有 SSE 分片 → 每个分片提取 `data` 字段 → 拼接所有 base64 → 一次性 decode → 完整 MP3

**VoiceRobot 项目启示：** 火山引擎有闭源 `speechengine_tob` SDK，内部处理了 STT → LLM → TTS 全链路。不适用于我们（我们的 STT 已用 WebSocket 实现，状态机是自己写的，不需要引入一个不透明的黑盒 SDK）。但验证了火山引擎 `openspeech.bytedance.com` 平台本身的稳定性。
