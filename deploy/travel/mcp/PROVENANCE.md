# Browser and MCP source

The MCP image builds [xpzouying/xiaohongshu-mcp](https://github.com/xpzouying/xiaohongshu-mcp) at commit `a5c8f7799980ba1fdd501999843eb2d17e4c9a9f`, applies `tools/windows/mcp-compat/compat.patch`, and copies its new source files. Its Apache-2.0 license is copied into the image.

`local-headless/` supplies the previously local replacement module required by that patch: `github.com/xpzouying/headless_browser` based on v0.4.0, with the standard-browser compatibility change. Its MIT license is included. The forced standard mode keeps Chromium's sandbox and automation disclosure; it clears fingerprint, user-agent, injected stealth scripts and arbitrary extra flags. It creates separate browser profiles and restores only this MCP service's own cookie file.

`seccomp-chromium.json` is derived from [Microsoft Playwright v1.56.1](https://github.com/microsoft/playwright/blob/v1.56.1/utils/docker/seccomp_profile.json), licensed Apache-2.0 (`PLAYWRIGHT-LICENSE`). The original upstream SHA-256 is `cc3e61cabda6bbc1e53e54d27ba4d55a9d3be829b6dd1a596f4a7b31b1cc7849`.

Local change (2026-11-04): add `chroot` to the first unconditional `SCMP_ACT_ALLOW` rule alongside `clone`, `setns` and `unshare`, and update that rule's comment. All other upstream rules remain unchanged. SHA-256 of the locally modified file (LF line endings): `b188e45ea4ff1f67d046aeb6923bd6d0eef54e8f6c9c00514df5d9532a541971`.

This addresses a Chromium 156 startup failure observed on the Debian 13 cloud host with `cap_drop: [ALL]`: the upstream `chroot` rule is conditional on the container retaining `CAP_SYS_CHROOT`, so Docker omits it under this deployment. Chromium's own [`ChrootToSelfFdinfo` / `DropFileSystemAccess` implementation](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/sandbox/linux/services/credentials.cc) calls `chroot("/proc/self/fdinfo/")` during sandbox setup. Allowing this syscall in the outer filter lets that isolation step reach the kernel.

The change expands the outer allowlist by one syscall; it does not grant a host capability or make the profile unconfined. `SCMP_ACT_ERRNO`, non-root execution, `cap_drop: [ALL]`, `no-new-privileges` and Chromium's sandbox stay enabled. The [kernel still requires `CAP_SYS_CHROOT` in the calling process's user namespace](https://man7.org/linux/man-pages/man2/chroot.2.html); capabilities in a newly created [user namespace do not confer capabilities in the parent/initial namespace](https://man7.org/linux/man-pages/man7/user_namespaces.7.html). This is not a claim that `chroot` alone provides a complete security boundary. No unconditional `mount` or `ptrace` rule is added. The upstream profile's separate `ptrace` allowance on kernels >=4.8 remains unchanged, so dropping host capabilities must not be described as denying every `ptrace` operation.

Runtime image tags were checked against the [official Node catalog](https://github.com/docker-library/official-images/blob/master/library/node), [Go catalog](https://github.com/docker-library/official-images/blob/master/library/golang), and [Caddy catalog](https://github.com/docker-library/official-images/blob/master/library/caddy): Node `24.22.2-bookworm-slim`, Go builder `1.26.10-bookworm`, Caddy `2.11.7-alpine`. Tags are version-pinned, not immutable digest locks; Debian's Chromium package is installed from its current signed repository for security updates.
