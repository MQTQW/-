# Browser and MCP source

The MCP image builds xpzouying/xiaohongshu-mcp at commit `a5c8f7799980ba1fdd501999843eb2d17e4c9a9f`, applies `tools/windows/mcp-compat/compat.patch`, then copies the public `tools/windows/mcp-compat/files/.` overlay to the same source paths. The overlay includes the replacement `xiaohongshu/search.go` and optional integration tests. Its Apache-2.0 license is copied into the image. [Upstream repository](https://github.com/xpzouying/xiaohongshu-mcp).

The search overlay bounds first-screen stability waiting with a 5-second child context and retains the parent 60-second search context. When that short wait expires on an unfiltered search, it waits for the first nonempty supported `feeds.value` or `feeds._value` array within the parent context. A stable empty result keeps its existing empty-result behavior. Diagnostic fields contain phase timings, fixed route/readiness values, booleans and array counts.

For a Windows source build, apply the original patch and copy this overlay to the same source paths. The normal Docker build performs that sequence. The Windows launcher uses a prebuilt executable, which requires rebuilding to pick up source changes. Cached-source and vendor-offline builds copy the overlay after unpacking their verified archives. The cached-source archive retains SHA-256 `96cfedb5c3888e9952944bb3b9fb08330b91ec53c0dac6bea3b72037121e9563`. The final search overlay has SHA-256 `eae20abce4843ab7f5e7037807c2852ae657a71ac45f30a8929bc119e4ce7f17`, and the final integration test source has SHA-256 `6c5ff00a94ba9cd437832e4131c79db6f3e3338d5e4710cb3cfe5dd124a56c7d`.

`local-headless/` supplies the previously local replacement module required by that patch, `github.com/xpzouying/headless_browser` based on v0.4.0, with the standard-browser compatibility change. Its MIT license is included. The forced standard mode keeps Chromium's sandbox and automation disclosure. It clears fingerprint, user-agent, injected stealth scripts and arbitrary extra flags. It creates separate browser profiles and restores only this MCP service's own cookie file.

`seccomp-chromium.json` is derived from [Microsoft Playwright v1.56.1](https://github.com/microsoft/playwright/blob/v1.56.1/utils/docker/seccomp_profile.json), licensed Apache-2.0 (`PLAYWRIGHT-LICENSE`). The original upstream SHA-256 is `cc3e61cabda6bbc1e53e54d27ba4d55a9d3be829b6dd1a596f4a7b31b1cc7849`.

The local change on 2026-11-04 adds `chroot` to the first unconditional `SCMP_ACT_ALLOW` rule alongside `clone`, `setns` and `unshare`, and updates that rule's comment. The locally modified file with LF line endings has SHA-256 `b188e45ea4ff1f67d046aeb6923bd6d0eef54e8f6c9c00514df5d9532a541971`.

This addresses a Chromium 156 startup failure observed on the Debian 13 cloud host with `cap_drop: [ALL]`. The upstream `chroot` rule is conditional on the container retaining `CAP_SYS_CHROOT`, so Docker omits it under this deployment. Chromium's own `ChrootToSelfFdinfo` / `DropFileSystemAccess` implementation calls `chroot("/proc/self/fdinfo/")` during sandbox setup. Allowing this syscall in the outer filter lets that isolation step reach the kernel. [Chromium implementation](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/sandbox/linux/services/credentials.cc).

The change expands the outer allowlist by one syscall. `SCMP_ACT_ERRNO`, non-root execution, `cap_drop: [ALL]`, `no-new-privileges` and Chromium's sandbox stay enabled. The kernel checks `CAP_SYS_CHROOT` in the calling process's user namespace. A new user namespace has capabilities scoped to that namespace and its descendants. The upstream profile separately allows `ptrace` on kernels >=4.8, with kernel permission checks applying to the operation. [chroot kernel checks](https://man7.org/linux/man-pages/man2/chroot.2.html), [user namespace capability scope](https://man7.org/linux/man-pages/man7/user_namespaces.7.html).
